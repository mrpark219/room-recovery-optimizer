# Room Recovery Optimizer

> **객실 이용 불가 상황 발생 시, 확정 예약을 최대한 유지하고 추가 운영 비용을 최소화하는 재배정 최적화 도구**

---

## 1. 문제 정의 및 배경

### 📌 문제 배경

- 반려동물 동반 숙소 예약 플랫폼을 개발하고 운영하면서 시설 고장, 누수 등 예기치 못한 문제로 인해 예약된 객실을 정상적으로 제공하기 어려운 상황을 경험했습니다.
- 반려동물 동반 숙소는 독채 숙소인 경우가 많아 대체 객실을 확보하기 어려웠고, 예약 취소로 인한 고객 불편과 매출 감소가 발생할 수 있었습니다.
- 이러한 경험을 바탕으로 레지던스형 숙소나 호텔처럼 여러 객실을 운영하는 환경에서는 **같은 객실 타입이나 상위 객실 타입으로 재배정해 예약 취소에 따른 피해를 최소화할 수 있지 않을까** 생각했습니다.
- 긴급한 상황에서 객실 재배정 방안을 빠르게 결정하다 보면 더 많은 예약을 유지하거나 추가 비용을 줄일 수 있는 조합을 놓칠 수 있어, 전체 예약과 가용 객실을 함께 고려할 필요가 있었습니다.

### ❗️중요한 이유

- **신속한 대응:** 돌발 상황에서 빠르게 대안을 찾아 피해를 수습해야 한다.
- **운영 비용 최소화:** 불필요한 상위 객실 타입 배정을 피하고, 보상 비용을 줄여야 한다.
- **브랜드 신뢰 유지:** 예약 취소를 최소화하여 고객 경험과 브랜드 신뢰도를 유지해야 한다.

### 🎯 목표

- 여러 예약의 조건과 가용 객실을 함께 고려하여 **최대 수용 + 최소 추가 비용**을 만족하는 재배정 계획을 도출한다.

## 2. 구현 범위

### 숙소, 객실 타입, 예약

- 한 숙소에는 여러 객실 타입이 있고, 각 타입에 실제 객실이 속한다. 고객은 객실 타입을 예약하고, 운영자는 숙박 구간별로 실제 객실을 배정한다.
- 한 예약에는 객실 타입을 하나만 저장한다.
- 숙소, 객실 타입, 객실을 등록하는 기능과 예약에 객실을 배정하는 기능은 이번 구현 범위에서 제외한다.

### 재배정 대상

- 객실 배정을 마친 뒤 장애가 발생한 상황을 다룬다. 이미 배정된 객실의 이용 불가 기간이 숙박 구간과 겹치는 예약을 재배정 대상으로 삼는다.
- 미배정 예약은 재배정 대상에서 제외한다.

### 재배정 처리

1. 운영자가 이용할 수 없는 객실과 장애 기간을 등록한다. 재배정 기준일을 선택하고 `변경이 필요한 예약 찾기`를 누르면 영향받는 예약과 예상 추가 비용을 확인할 수 있다.
2. `재배정 제안 검토 시작`을 누르면 예약별로 기존 일정과 추천 일정을 비교할 수 있다. 운영자는 추천 일정을 사용하거나 화면에 표시된 대체 객실을 직접 선택한다.
3. 운영자가 고객의 수락을 기록하면 서버가 새 배정이 현재 등록된 객실 장애와 겹치는지 확인하고, 충돌이 없으면 배정을 저장한다. 고객이 취소를 요청하면 해당 예약을 취소하고 나머지 예약의 재배정안을 다시 계산한다.
4. 운영자는 실제 객실 이동이 끝날 때마다 이동 완료를 기록한다. 수락, 취소, 이동 완료 결과는 복구 이력에서 확인할 수 있다.

### 설계 범위 및 제약

- 재배정은 숙소 단위로 진행한다. 장애의 영향을 받지 않은 예약은 기존 배정을 유지하고, 대체 객실은 기존 예약의 숙소 안에서만 찾는다.
- 제안은 재배정 세션을 시작할 때 등록된 장애를 기준으로 계산한다. 고객이 수락할 때 새 배정이 현재 장애와 겹치면 기존 배정을 유지한 채 제안을 다시 계산한다.
- 같은 운영사가 가까운 곳에 여러 숙소를 운영한다면 다른 지점의 빈 객실도 재배정 후보로 고려할 수 있다. 다만 이번 구현에서는 한 숙소 안에서 기존 예약을 유지하는 흐름에 집중했다.

### 재배정 알고리즘

1. 예약 시작일과 재배정 기준일 중 늦은 날부터 체크아웃 전날까지 대체 객실을 찾는다. 예약한 타입과 같거나 상위 등급의 객실 타입에 속하고, 투숙 인원을 수용할 수 있으며, 해당 날짜에 장애나 다른 예약이 없는 객실만 후보로 둔다.
2. 백트래킹으로 예약별 객실을 하나씩 배정해 남은 숙박을 모두 채울 수 있는 조합을 탐색한다. 숙박 중 객실을 바꾸는 일정도 고려하되, 같은 날짜에 같은 객실이 중복되는 배정은 건너뛴다. 남은 예약을 모두 수용해도 당일 이동 대상의 수용 건수와 전체 수용 건수를 기준으로 현재 최선의 안을 따라잡을 수 없으면 해당 조합의 탐색을 중단한다.
3. 여러 재배정안이 나오면 당일에 객실을 옮겨야 하는 예약을 더 많이 유지할 수 있는 안을 먼저 고른다. 그 수가 같으면 전체 예약을 더 많이 유지하는 안을 고르고, 이후 객실 이동 횟수가 적은 안, 예상 추가 비용이 낮은 안 순으로 비교한다. 최종안에서 객실을 배정받지 못한 예약은 화면에 `대체 객실 없음`으로 표시한다.

- 예상 추가 비용은 남은 숙박의 대체 객실 기준가 합계에서 기존에 예약한 객실 타입의 기준가 합계를 뺀 금액이다.
- 숙박일이나 후보 객실이 늘면 탐색할 조합이 많아지므로 알고리즘 개선이 필요할 수 있다.

## 3. 예시

데모의 한강 호텔을 예로 들어, 객실 배정 방식에 따라 유지할 수 있는 예약이 어떻게 달라지는지 확인하는 예시다.

### 객실 구성

| 객실 타입 | 객실                | 1박 기준가 |
|-----------|---------------------|-----------:|
| Standard  | 101호, 102호, 103호 |  100,000원 |
| Deluxe    | 201호               |  150,000원 |

### 기존 예약

| 예약 | 체크인 | 체크아웃    | 기존 객실 |
|------|--------|-------------|-----------|
| #1   | 11/09  | 11/12 (3박) | 101호     |
| #2   | 11/10  | 11/13 (3박) | 102호     |
| #3   | 11/10  | 11/12 (2박) | 103호     |

201호는 예약이 없다. 체크아웃 날짜는 숙박에 포함하지 않는다.

### 객실 장애

재배정 기준일을 2026년 11월 11일로 두고, 다음과 같이 장애가 발생했다고 가정한다.

| 객실  | 장애 시작일 | 장애 종료일 | 이용할 수 없는 숙박일 |
|-------|-------------|-------------|-----------------------|
| 101호 | 11/11       | 11/12       | 11일 밤               |
| 102호 | 11/12       | 11/13       | 12일 밤               |

예약 #1은 이미 투숙 중이며 11일에 바로 객실을 옮겨야 한다. 예약 #2는 11일 밤에 기존 객실을 쓸 수 있지만 12일 밤에는 대체 객실이 필요하다. 예약 #3은 기존 일정을 유지하며, 103호는 #3이 체크아웃하는 12일부터 비어 있다.

### 재배정 결과 비교

| 비교                                              | 예약 #1                       | 예약 #2                      | 결과                                       |
|---------------------------------------------------|-------------------------------|------------------------------|--------------------------------------------|
| #2를 먼저 처리해 이동 없는 일정을 배정한다고 가정 | 11일 밤에 배정할 객실이 없다. | 11일과 12일 밤 모두 201호    | **1건 유지, 1건 미해결**                   |
| 두 예약을 함께 검토                               | 11일 밤 201호                 | 11일 밤 102호, 12일 밤 101호 | **2건 모두 유지**, 예상 추가 비용 50,000원 |

#2의 일정만 보면 201호에서 남은 2박을 보내는 편이 객실 이동을 줄인다. 하지만 11일 밤에는 102호와 103호에 기존 배정이 있어 #1이 옮길 수 있는 객실은 201호뿐이다. 추천안은 #1에 11일 밤 201호를 배정하고, #2는 12일에 장애가 끝난 101호로 옮겨 두 예약을 모두 유지한다.

## 4. Docker로 실행

```bash
docker compose up --build --wait
```

이미지를 먼저 빌드한 후 실행할 수도 있다.

```bash
./scripts/build-images.sh
docker compose up --no-build --wait
```

- 프런트엔드는 [http://localhost:3000](http://localhost:3000), 백엔드 API는 [http://localhost:8080/api/accommodations](http://localhost:8080/api/accommodations)에서 확인할 수 있다.
- MySQL은 로컬 3307 포트에 연결된다. 기본 프로필은 데모 데이터를 사용하는 `demo`다.
- `docker compose down`은 컨테이너와 네트워크를 제거하고 MySQL 볼륨은 유지한다.
- 데이터를 초기화하려면 `docker compose down -v`를 실행한다.

## 5. AI 활용

### 1. 문제 정의

숙소 예약을 운영하면서, 객실 장애로 확정된 예약을 옮기거나 취소해야 할 때 어떤 예약을 어느 객실로 옮겨야 피해를 줄일 수 있을지 빠르게 판단하기 어렵다고 생각했습니다. 이 판단을 돕는 도구를 만들기로 하고, AI와 가능한 대응 방안과 구현에 필요한 조건을 검토했습니다. 이번 구현에서는 같은 숙소 안의 가용 객실을 바탕으로 재배정안을 찾는 흐름으로 범위를 정했습니다.

### 2. 요구사항 구체화

객실 장애로 인한 예약 취소를 줄이려면 어떤 예약부터 처리하고 어떤 배정안을 선택해야 하는지 AI와 문답했습니다. 이미 투숙 중인 고객을 어떻게 우선할지, 한 객실에서 남은 숙박을 이어가는 안과 중간에 객실을 옮기는 안을 어떻게 비교할지 검토했습니다. 당일 이동이 필요한 예약과 전체 예약의 유지 건수가 같다면, 추가 비용이 더 들더라도 고객이 객실을 덜 옮기는 안을 우선하기로 했습니다.

### 3. 설계와 구현

정한 배정 기준을 바탕으로 AI와 재배정 알고리즘을 설계했습니다. AI에 알고리즘의 흐름을 의사코드로 설명해 달라고 요청하고, 배정 조건과 우선순위가 설계에 반영됐는지 확인했습니다. 운영 흐름에 필요한 화면을 기획하고 각 화면에서 사용할 API를 설계했습니다. 이후 AI에 단계별 구현을 맡기고, 재배정 조건과 우선순위를 적용하는 핵심 코드를 중심으로 리뷰했습니다.

### 4. 검증과 개선

테스트 시나리오를 만드는 에이전트, 시나리오를 실행하는 에이전트, 계산 결과를 검토하는 에이전트를 각각 두고 결과가 예상과 일치하는지 확인했습니다. 화면은 직접 사용해 보면서 UI와 사용 흐름을 개선했습니다.
